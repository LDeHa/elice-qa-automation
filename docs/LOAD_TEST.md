# 부하 테스트 클라이언트 모니터링

## 목표와 역할

팀 목표는 30명 동시 접속에서 Error Rate 1% 미만, 평균 Latency 1초 이내를 확인하는 것이었습니다. 제 역할은 JMeter를 실행하는 VM의 CPU·메모리를 `htop`으로 관찰하여 부하 생성 환경 자체가 병목인지 판단하는 것이었습니다.

## 실행 단계와 중단 기준

- 가상 사용자: 5 → 10 → 20 → 30명
- HTTP 500 발생 시 즉시 중단
- 실제 브라우저에서 뚜렷한 응답 지연이 체감되면 공유 후 중단 판단
- CPU 90% 이상이 지속되거나 메모리가 계속 증가하면 부하 생성기 한계 가능성 보고

## 관찰 결과

선별한 고부하 프레임에서 메모리는 약 `921~974 MiB / 15.6 GiB` 범위였고 Swap 사용은 없었습니다. 일부 코어 또는 JMeter 스레드가 순간적으로 약 `60~98%`까지 상승했지만, 8 vCPU 전체가 지속적으로 포화되는 모습이나 메모리 누적 증가는 확인되지 않았습니다.

따라서 캡처 구간에서는 **JMeter VM의 메모리 부족이나 전체 CPU 포화가 주요 병목이라고 볼 근거가 부족하다**고 판단했습니다. 단, 이는 서버 CPU·DB·애플리케이션 로그를 대신하는 결과가 아니며 클라이언트 병목 가능성을 배제하기 위한 보조 증거입니다.

| 단계 | 메모리 관찰 | CPU 관찰 | 클라이언트 병목 판단 |
| --- | --- | --- | --- |
| 5명 | 약 974 MiB / 15.6 GiB | 단일 코어 순간 피크 관찰 | 전체 포화 근거 없음 |
| 10명 | 약 938 MiB / 15.6 GiB | JMeter 스레드 순간 피크 관찰 | 전체 포화 근거 없음 |
| 20명 | 약 921 MiB / 15.6 GiB | 여러 스레드에 부하 분산 | 전체 포화 근거 없음 |
| 30명 | 약 959 MiB / 15.6 GiB | 단일 코어/스레드 순간 피크 관찰 | 전체 포화 근거 없음 |

> 수치는 htop 녹화에서 선별한 프레임의 순간값입니다. 지속 시간 기반 평균이나 서버 성능 수치로 해석하면 안 됩니다.

## 공개 자료에서 원본을 제외한 이유

원본 영상과 캡처에는 VM 사용자명, 프로세스 실행 경로, 프로젝트명 등 환경 정보가 포함됩니다. 포트폴리오에는 수치와 판단 근거만 익명화해 기록하고 원본은 비공개 증빙으로 보관합니다.

## 측정 한계

- DEV 서버 CPU·메모리 접근 권한 없음
- DB Connection과 Slow Query 접근 권한 없음
- 서버 Exception 로그 접근 권한 없음
- htop은 순간 관찰이며 시계열 수집 도구가 아님

후속 프로젝트에서는 부하 생성기와 대상 서버 모두에 Prometheus/Grafana 또는 동일한 시계열 지표를 연결하고, JMeter 결과와 시간축을 맞춰 분석하는 방식을 적용할 수 있습니다.
